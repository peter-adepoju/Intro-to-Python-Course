Week 14, Day 2

Edge cases

Most bugs don’t live in the ordinary inputs a program was written for. They live at the edges: the empty list, the single item, the tie, the negative number, the first and last positions, the input exactly on a boundary. Today you’ll learn a checklist for finding edge cases before your users do, and practise writing checks that catch the bugs hiding there.

By the end of today you can

  • Explain why ordinary examples can hide bugs, and where bugs cluster
  • Use a checklist to list the edge cases of a problem before coding
  • Write checks for edge cases that catch broken versions of a function
  • Decide what a function should do at each edge, and make the decision visible
  • Fix functions that fail at the edges without breaking the ordinary cases

Warm-up

The function is right for every list you’d think of first. Then one empty list arrives and the whole program stops. That single input is an edge case: an input at the edge of what the problem allows, where the usual reasoning stops working.

Where bugs live

Here’s a function that should return the second-largest different value in a list, or None if there isn’t one. Four people wrote it. Every version passes the first two examples, the ones anybody would try first:

Each wrong version has exactly the kind of bug that lives at an edge:

  • sort_only forgets that values can repeat: the second-largest of [9, 9, 4] is 4, not 9.
  • start_at_zero assumes values are positive: with all negatives, nothing ever beats the starting 0.
  • no_checks forgets the lists that are too short to have an answer at all.

None of these would be found by [3, 9, 4] or [10, 20, 30]. Ordinary examples check that the idea is right. Edge cases check that the code is right.

Key idea

Bugs cluster at the edges: empty and single inputs, repeats and ties, zero and negatives, the first and last positions, and exact boundaries. Test there on purpose.

A checklist

You won’t think of edge cases reliably by waiting for inspiration. Go through a checklist. Not every line applies to every problem, but asking each question takes a minute:

Ask about Examples
Zero, one, many an empty list, string or file; exactly one item; two items (the smallest case with a “between”)
Same and ties all items equal; duplicates; two items tied for best
Signs and zero negative numbers, zero, a mix
First, last, middle the thing you’re looking for is at the very start, the very end, or not there at all
Boundaries exactly on a limit (a mark of exactly 50, a time of exactly 00:00), and one either side
Order already sorted, sorted backwards, all shuffled
Size very large values, very long inputs (is it still fast enough?)
Text spaces at the ends, upper and lower case, punctuation, accents and other alphabets, an empty string
Bad input the wrong type, a format that’s nearly right, a missing file

Apply it to a small problem: “Return the longest word in a sentence.”

  • Zero, one, many: "" (no words: ""? None? an error?), "hello".
  • Ties: "cat dog": the first, the last, or both?
  • Text: " hi there " (extra spaces), "Hello, world!" (does the comma count as part of the word?).
  • First, last: the longest word at the start, and at the end.

Four of those are decisions the one-sentence description didn’t make. That’s normal; Day 1 said how to handle it.

Deciding what should happen

For each edge case there are only a few sensible behaviours:

  1. There’s a natural answer: the sum of an empty list is 0; the longest word of "" could reasonably be "".
  2. Return a value meaning “none”: None, as second_largest does. Simple, but every caller must remember to check for it.
  3. Raise an exception: the average of nothing doesn’t exist, so raise ValueError(...). Clear, and it can’t be ignored by accident.
  4. It can’t happen: you’ve checked earlier in the program that the list is never empty. Then say so in the docstring, and perhaps with an assert.

What’s never acceptable is behaviour nobody decided: an IndexError from deep inside, or a confident wrong answer like start_at_zero’s 0.

Notice where the decisions went: the docstring states them, and a check pins each one down. > (not >=) is what makes the first of several tied words win; a check makes sure nobody “tidies” it into >= later.

Boundaries

A boundary is a value where the behaviour changes: a pass mark, a size limit, the last valid index. Off-by-one mistakes (< instead of <=, range(n) instead of range(n + 1)) are the commonest bugs of all, and they only show up on the boundary.

The rule is to test three values at every boundary: just below, exactly on, and just above.

If the description had said “children 12 and under”, then 12 would be the one value that changes: only a check exactly on the boundary can tell the two rules apart.

Tip

For a range of valid values (0 to 100, say), test both ends and one step outside each: -1, 0, 100, 101. Four checks catch nearly every off-by-one mistake in a range check.

Practice

Exercise10 points
Edges of a sum

Write sum_of_evens(values) that returns the sum of the even numbers in a list. Then make sure it handles: an empty list, no even numbers, negative even numbers, and zero. (It’s simple; the point is to check those cases yourself before pressing Check.)

Exercise20 points
Checks that catch

chunks(items, n) splits a list into pieces of n items, the last piece possibly shorter: chunks([1, 2, 3, 4, 5], 2) is [[1, 2], [3, 4], [5]]. For n less than 1 it raises a ValueError. Write chunk_checks() with asserts that pass for the correct version below and catch each of five broken versions, one for each kind of edge: an empty list, a list that divides exactly, n larger than the list, n of 1, and a bad n of 0.

Exercise15 points
Do they overlap?

Write overlap(a, b) for two time ranges, each a tuple (start, end) of minutes with start < end, that returns how many minutes they share (0 if none). Ranges that only touch, like (0, 60) and (60, 90), share 0 minutes. Before coding, list the edge cases: one range inside the other, identical ranges, touching, the second before the first.

Exercise10 points
Initials, carefully

Write initials(name) that returns the capitalised initials of each word of a name, with no dots: "ada lovelace" gives "AL". Handle: extra spaces anywhere, an empty or blank name (""), a single name, names that are already capitalised, and hyphenated names, where each part counts ("Mary-Jane Watson" gives "MJW").

Exercise10 points
On the boundary

A mark from 0 to 100 gets "distinction" from 70, "pass" from 40, otherwise "fail"; anything outside 0 to 100 raises a ValueError. Write band(mark). Then, before checking, write down the eight marks that test every boundary from both sides, and try them yourself.

Bug hunt10 points
Only works in the middle

neighbours_sum(values, i) should return the sum of the items either side of position i, treating missing neighbours as 0: for [1, 2, 3], position 0 gives 2, position 1 gives 4, position 2 gives 2. It’s wrong at both ends. Fix it.

Bug hunt10 points
Most common

most_common(items) should return the most common item, the one that appears first in the list if several tie, or None for an empty list. It fails two edge cases. Find them with your own examples, then fix it.

Bug hunt10 points
Words that end the text

count_word(text, word) should count how many times word appears as a whole word, ignoring case and the punctuation .,!?. It misses some. Find the edge it fails on, and fix it.

Arrange the lines for safe_max, which returns the largest value, or default for an empty list, and works for negative numbers. One line is a trap.

Exercise25 points
Challenge: merging intervals

Calendar apps merge overlapping bookings to show when someone is busy. Write merge_intervals(intervals) that takes a list of (start, end) tuples with start <= end, in any order, and returns a sorted list of merged intervals in which none overlap or touch: [(1, 3), (2, 6), (8, 10), (10, 12), (15, 18)] gives [(1, 6), (8, 12), (15, 18)]. Before writing it, list the edge cases: empty, one interval, one inside another, identical ones, touching, unsorted input, zero-length intervals like (5, 5). Don’t change the list you’re given.

Before you go

Choose any function you’ve written this year and run it through the checklist. Write a check for each edge case that applies, and fix anything that fails. You’ll almost certainly find something. Tomorrow: pseudocode, a way to plan an algorithm in plain words before you commit to code.
